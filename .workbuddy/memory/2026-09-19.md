## 迁移 Godot 可行性评估（仅调研，未动代码）
- 代码构成：逻辑/数据 ~3969 行（52%，config/waves/codex/enemies/towers/main/grid/resonance/ui/audio），画面绘制 ~3624 行（48%，render 1672 + monsters 750 + fx 493 + icons 212 + util 113 + runtime 384）。
- 真正要重写的是 render+monsters+fx ≈ 2915 行绘制 + audio.js 478 行 WebAudio 合成；纯逻辑（状态机/BFS 流场/共振/波次）可平移。
- **关键结论：Godot 官方不支持微信小游戏导出**（官方只有 Web 导出，依赖 WASM+WebGL2+浏览器 API，产物不能直接进微信开发者工具）。社区方案：godot-minigame / Godot工具箱(get.godots.app) / godot-cn 整合包，原理是在小游戏里跑一套 Godot WASM + 加载 pck.bin。
- 社区实测坑：需锁定 Godot 4.4~4.6.2 并自行编译引擎（4.7 在 iPhone 微信基础库 3.17 因 Wasm EH section 不解析直接崩，需把 SUPPORT_LONGJMP 从 wasm 改 emscripten）；单线程 wasm（无 SharedArrayBuffer）；音频后端要回退 ScriptProcessor；真机内存占用大（实测 ~1.9GB）、首屏加载慢；`user://` 空文件会让 JSON.parse 喷红错。
- 建议路线（未拍板）：A 全量移植 Godot（重写画面+音频，导出链有坑）；B 保留现有 JS/Canvas，只做微信适配（现状）。

## 引擎选型调研：谁能直接导出微信小游戏（官方文档口径）
- 微信官方《微信小游戏引擎适配概述》明列支持：Cocos Creator / LayaAir / Egret（**官方内置适配**）、Unity 与团结引擎 / Cocos2d-x / Unreal（**WebAssembly 转换适配**）。**Godot 不在列**（只有社区方案）。
- Cocos Creator 的运行时内置于微信客户端，**不占 4MB 主包限额**，这是它相对 Unity/WASM 方案的最大结构性优势。
- 按本项目（纯 Canvas 2D + ES5 JS，7593 行）的代码转换难度排序：原生 JS/Canvas（现状，≈0 改造）< PixiJS/Phaser+适配层 < Cocos Creator(TS) ≈ LayaAir(TS) < Egret(TS，生态萎缩) < Cocos2d-x(C++) < Unity/团结引擎(C#+WASM，包体大内存高)。
- 结论：目标只要微信小游戏 → 保持现有 JS/Canvas 最省；若确实要上引擎，**唯一值得考虑的是 Cocos Creator（TS 同族、官方一键发布、不占主包）**；Unity 对纯 2D 塔防是杀鸡用牛刀。
